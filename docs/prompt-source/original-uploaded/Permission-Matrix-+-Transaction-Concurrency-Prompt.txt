# 1. SECURITY PRINCIPLE

Không được coi frontend là lớp bảo mật.

Các cơ chế sau chỉ phục vụ UX:

```text
hide button
disable button
hide menu
```

Không phải security boundary.

Backend phải enforce permission.

Nếu user gọi trực tiếp:

```text
POST /admin/stock/adjust
```

thì backend vẫn phải kiểm tra quyền.

→ sử dụng permission/action + Voter.

# 3. PERMISSION MODEL

Phân biệt:

### Role

Ví dụ:

```text
ROLE_USER
ROLE_ADMIN
```

### Permission / Capability

Ví dụ:

```text
POS_CHECKOUT
ORDER_VIEW
ORDER_CANCEL
ORDER_REFUND
PRODUCT_MANAGE
PRODUCT_PRICE_CHANGE
STOCK_ADJUST
DEBT_PAYMENT
AUDIT_VIEW
SESSION_VIEW
SESSION_REVOKE
USER_MANAGE
```

Không nhất thiết lưu permission thành database nếu MVP có static permission matrix.

Phải đánh giá:

* static role hierarchy có đủ không?
* cần Voter không?
* cần database permission không?

Ưu tiên giải pháp đơn giản nhất đáp ứng requirement.

# 4. ACTION-LEVEL AUTHORIZATION

Permission phải được thiết kế theo business action.

Không chỉ:

```text

```

mà phải phân biệt:

```text
Can view product
Can create product
Can edit product
Can change price
Can deactivate product
```

Tương tự Order:

```text

Can refund order
```

# 7. SELF VS OTHER RESOURCE

Phải phân biệt action trên chính user và user khác.

Ví dụ:

```text
User có thể logout session của chính mình.
Admin có thể revoke session của user khác.
```

Nếu cần:

```text
SESSION_REVOKE_SELF
SESSION_REVOKE_OTHER
```

thì đề xuất.

Không tạo permission thừa nếu logic resource ownership có thể xử lý bằng Voter.

# 8. RESOURCE OWNERSHIP

Phân tích ownership:

### Order

User có được xem mọi Order hay chỉ Order của mình?

### Customer

User có được sửa mọi Customer?

### Debt

User có được thu mọi Debt?

### Session

User có được xem/revoke session của chính mình?

User có được xem audit của chính mình hay chỉ Admin?

```text

```

Không được chỉ dựa trên route prefix.

Ví dụ:

```text

```

không phải business authorization.

Authorization phải gắn với action.

# 11. STOCK AUTHORIZATION

Phân biệt:

```text
STOCK_VIEW
```

và:

```text
STOCK_ADJUST
```

User có thể xem stock nhưng không được thay đổi stock nếu không có permission.

Sale deduction không phải manual stock adjustment.

User bán hàng được bán sản phẩm nhưng không đồng nghĩa được phép chỉnh tồn kho.

---

# 12. PRODUCT PRICE AUTHORIZATION

Phải phân biệt:

```text
PRODUCT_EDIT
```

và:

```text
PRODUCT_PRICE_CHANGE
```

Nếu business requirement coi đổi giá là sensitive action:

→ Admin only.

Nếu User được phép sửa product information nhưng không được đổi giá:

→ permission riêng.

---

# 13. ORDER CANCEL / REFUND

Phải xác định:

```text
ORDER_CANCEL
ORDER_REFUND
```

là hai permission khác nhau.

Không gộp nếu business impact khác nhau.

Cancel:

* order state
* stock reversal
* debt/payment impact

Refund:

* financial reversal
* stock impact
* audit

---

# 14. DEBT PAYMENT

Xác định:

```text
DEBT_VIEW
DEBT_PAYMENT
```

là hai capability khác nhau.

Một User có thể xem công nợ nhưng không được thu tiền nếu requirement yêu cầu kiểm soát.

Nếu User được thu tiền:

→ vẫn phải audit.

# 15. AUDIT

```text
AUDIT_VIEW
```

chỉ dành cho actor phù hợp.

Không cho User:

* sửa
* xóa
* truncate
* alter audit history

AuditLog immutable.

# 17. SESSION MANAGEMENT

User:

```text
logout own session
```

Admin:

```text
view sessions
revoke sessions
```

Nếu Admin revoke session hiện tại:

→ xác định behavior.

Không để session revoked tiếp tục thực hiện request authenticated.

# 18. VOTER STRATEGY

Phân tích khi nào cần Symfony Voter.

Ví dụ:

```text
OrderVoter
ProductVoter
DebtVoter
SessionVoter
```

Không tạo Voter cho mọi Entity.

Chỉ dùng Voter khi permission phụ thuộc:

* resource
* ownership
* state
* actor
* business context

Ví dụ:

```text
Can cancel this Order?
```

không chỉ phụ thuộc role.

Có thể phụ thuộc:

```text
Order.status
User.role
Order.owner
```

---

# 19. STATE-AWARE AUTHORIZATION

Permission phải kết hợp State Machine.

Ví dụ User có:

```text
ORDER_CANCEL
```

nhưng:

```text
Order.status = CANCELLED
```

→ vẫn không được cancel.

Hoặc:

```text
Debt.status = PAID
```

→ không được tạo DebtPayment.

Authorization ≠ Business Rule.

Cả hai đều phải được kiểm tra.

# 26. ERROR SEMANTICS

Phân biệt:

### 401

Chưa authenticated.

### 403

Authenticated nhưng không có permission.

### 404

Resource không tồn tại hoặc có thể cố ý hide existence tùy security requirement.

### 409

Business/resource conflict.

### 422

Validation/business input error nếu architecture chọn semantics này.

Không expose sensitive internal details.
