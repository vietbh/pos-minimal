# CRITICAL PROMPT — PHÂN TÍCH USE CASE MOBILE POS

Bạn đang thiết kế nghiệp vụ cho một **Mobile-first POS nhỏ** sử dụng:

* Symfony 7.4
* MySQL
* Doctrine ORM
* Twig
* Stimulus
* Symfony Messenger
* Cronjob trên hosting

Hãy phân tích và thiết kế **Use Case đầy đủ cho MVP** dựa trên Critical Prompt của dự án.

## MỤC TIÊU

Tạo một bộ Use Case đủ rõ để từ đó có thể tiếp tục thiết kế:

1. Domain model
2. Entity
3. Database schema
4. Application Service
5. Controller/Route
6. Stimulus Controller
7. Messenger Message/Handler
8. Permission
9. Test case

**Không code ở bước này.**

Chỉ phân tích nghiệp vụ và interaction.

# 4. FORMAT MỖI USE CASE

Mỗi Use Case phải có cấu trúc:

## UC-XXX — Tên Use Case

### Goal

Mục tiêu nghiệp vụ.

### Actor

Ai thực hiện.

### Trigger

Điều gì bắt đầu Use Case.

### Preconditions

Điều kiện trước khi bắt đầu.

### Main Flow

Luồng thành công từng bước.

Ví dụ:

```text
1. User mở POS.
2. User search product.
3. User chọn product.
4. Stimulus thêm product vào local cart.
5. User thay đổi quantity.
6. Stimulus cập nhật UI.
7. User tap Checkout.
8. Client gửi một checkout request.
9. Backend validate dữ liệu.
10. Backend kiểm tra stock.
11. Backend tính lại total.
12. Backend tạo order/payment.
13. Backend trừ stock.
14. Transaction commit.
15. UI hiển thị success.
```

### Alternative Flows

Các trường hợp hợp lệ khác.

Ví dụ:

* thanh toán một phần
* ghi nợ
* khách chưa tồn tại
* nhiều phương thức thanh toán nếu hỗ trợ

### Exception Flows

Các trường hợp lỗi:

* product không tồn tại
* product inactive
* thiếu stock
* duplicate checkout
* database error
* session hết hạn

### Postconditions

Trạng thái hệ thống sau khi thành công.

### Data Changed

Entity/data nào bị tạo hoặc thay đổi.

### HTTP Requests

Phải chỉ rõ:

* request nào cần server
* request nào xử lý local bằng Stimulus
* request nào async

### Transaction Boundary

Chỉ rõ có database transaction hay không.

### Async Jobs

Nếu có Messenger job, chỉ rõ message được dispatch sau khi transaction thành công.

### Permission

Role/permission cần thiết.

### Audit

Có audit log hay không và audit action nào.

### Mobile UX Notes

Chỉ rõ cách thiết kế interaction trên mobile.

### Acceptance Criteria

Danh sách điều kiện để Use Case được coi là hoàn thành.

# 5. ĐẶC BIỆT PHÂN TÍCH POS CHECKOUT

Đây là Use Case quan trọng nhất.

Phải phân tích riêng:

## UC-POS-CHECKOUT

Phải mô tả chính xác:

### Input

* cart items
* product ID
* quantity
* customer ID optional
* payment method
* paid amount
* idempotency key

### Backend phải tự xác định lại

* product tồn tại
* product active
* current selling price
* stock
* subtotal
* total
* paid amount
* debt amount

Frontend total chỉ dùng cho UX.

### Transaction

Toàn bộ:

```text
Order
OrderItem
Payment
Debt
StockMovement
AuditLog
```

phải được xử lý trong transaction phù hợp.

### Concurrency

Phải mô tả cách tránh:

```text
Stock = 1

User A mua 1
User B mua 1
```

Không được để cả hai transaction thành công.

### Idempotency

Phải mô tả cách chống:

```text
User tap Checkout
User tap Checkout lần 2
```

không được tạo hai Order.

# 6. PHÂN TÍCH CART

Cart không phải database transaction.

Cart là UI state.

Phân tích rõ:

```text
Product search
      ↓
Stimulus
      ↓
Local cart
      ↓
UI calculation
      ↓
Checkout
      ↓
Backend authoritative validation
```

Các action:

* add
* increase quantity
* decrease quantity
* remove
* clear

phải ưu tiên **zero HTTP request**.

---

# 7. PHÂN TÍCH DEBT

Debt phải được thiết kế theo từng khoản phát sinh từ Order.

Không dùng:

```text
Customer.totalDebt
```

làm nguồn dữ liệu duy nhất.

Mô hình logic:

```text
Customer
 ├── Debt #001 → Order #1001
 ├── Debt #002 → Order #1010
 └── Debt #003 → Order #1050
```

Phải phân tích:

* tạo debt
* partial payment
* full payment
* overdue
* due date
* reminder
* debt history

Dư nợ customer có thể được tính từ các Debt còn outstanding.

| Use Case         | Entity đọc        | Entity tạo                | Entity cập nhật | Audit |
| ---------------- | ----------------- | ------------------------- | --------------- | ----- |
| Checkout         | Product           | Order, OrderItem, Payment | Product         | Yes   |
| Credit Sale      | Product, Customer | Order, OrderItem, Debt    | Product         | Yes   |
| Pay Debt         | Customer, Debt    | DebtPayment               | Debt            | Yes   |
| Stock Adjustment | Product           | StockMovement             | Product         | Yes   |

Không bỏ qua entity nào bị thay đổi.

# 16. EDGE CASES

Phải chủ động phân tích các edge case quan trọng:

### POS

* cart rỗng
* product bị inactive sau khi thêm vào cart
* price thay đổi sau khi thêm vào cart
* stock thay đổi sau khi thêm vào cart
* thiếu stock
* duplicate checkout
* network timeout sau khi backend đã commit
* user tap nhiều lần
* session hết hạn

### Debt

* payment bằng đúng remaining amount
* payment nhỏ hơn remaining
* payment lớn hơn remaining
* debt đã PAID
* debt overdue
* customer có nhiều debt

### Stock

* stock = 0
* adjustment âm
* adjustment làm stock âm
* concurrent sale
* cancel order hai lần

### Order

* cancel order đã cancelled
* cancel order đã refunded
* refund nhiều lần
* order không tồn tại

---

# 17. NETWORK FAILURE

Đặc biệt phân tích trường hợp:

```text
User checkout
      ↓
Backend commit thành công
      ↓
Network timeout
      ↓
Frontend không biết success
```

Không được thiết kế đơn giản bằng cách:

```text
Retry POST
```

vì có thể tạo duplicate order.

Phải sử dụng idempotency key hoặc cơ chế tương đương.

Frontend phải có flow an toàn để kiểm tra trạng thái transaction trước khi retry.

# 18. ACCEPTANCE CRITERIA

Mỗi Use Case phải có acceptance criteria có thể chuyển thành automated test.

Ví dụ:

```text
Given product stock = 10
When user buys quantity 3
Then order is completed
And stock becomes 7
And StockMovement is created
```

Hoặc:

```text
Given debt remaining = 100,000
When customer pays 40,000
Then DebtPayment = 40,000
And debt remaining = 60,000
And status = PARTIALLY_PAID
```

Acceptance criteria phải rõ ràng, deterministic và testable.
