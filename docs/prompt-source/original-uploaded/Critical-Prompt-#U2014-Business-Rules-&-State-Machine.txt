# 2. RULE CLASSIFICATION

Phân loại mọi rule thành:

## Validation Rule

Kiểm tra input.

Ví dụ:

```text
quantity > 0
amount > 0
name không rỗng
```

## Business Rule

Quy định nghiệp vụ.

Ví dụ:

```text
Không được bán quá tồn kho.
```

## Invariant

Điều kiện **luôn phải đúng** sau mỗi transaction hợp lệ.

Ví dụ:

```text
stockQuantity >= 0
```

## Authorization Rule

Ai được phép làm.

Ví dụ:

```text
Chỉ Admin được điều chỉnh stock.
```

## Transaction Rule

Những thay đổi nào phải commit/rollback cùng nhau.

Ví dụ:

```text
Order + Payment + StockMovement
```

## Async Rule

Việc nào được xử lý sau bằng Messenger.

Phải phân loại rõ.

# 7. DEBT RULES

Debt chỉ tồn tại khi:

```text
order.total > totalPaid
```

và:

```text
customer != null
```

Không được tạo anonymous debt.

---

## 7.1 Debt invariant

Luôn phải đúng:

```text
originalAmount >= 0
paidAmount >= 0
remainingAmount >= 0
```

và:

```text
originalAmount
=
paidAmount + remainingAmount
```

nếu không có overpayment.

---

# 8. DEBT PAYMENT RULES

Khi thanh toán:

```text
amount > 0
amount <= debt.remainingAmount
```

Sau transaction:

```text
newPaidAmount
=
oldPaidAmount + payment.amount
```

và:

```text
newRemainingAmount
=
originalAmount - newPaidAmount
```

Nếu:

```text
remainingAmount = 0
```

→ Debt chuyển:

```text
PAID
```

Nếu:

```text
0 < remainingAmount < originalAmount
```

→:

```text
PARTIALLY_PAID
```

Nếu chưa có payment:

```text
OPEN
```

# 9. OVERDUE RULE

Không nhất thiết persist `OVERDUE`.

Ưu tiên derived condition:

```text
remainingAmount > 0
AND dueDate IS NOT NULL
AND dueDate < current time
```

→ khoản nợ đang quá hạn.

Phải phân tích:

* dueDate null
* dueDate hôm nay
* timezone
* payment đúng ngày due
* payment sau due date

Không dùng cron để "đổi trạng thái overdue" nếu trạng thái có thể tính được.

# 25. IDEMPOTENCY

Mobile có thể gặp:

```text
User tap checkout
↓
Network timeout
↓
User tap again
```

Không được tạo hai Order.

Mỗi checkout request phải có:

```text
idempotencyKey
```

hoặc cơ chế tương đương.

Phải xác định:

* key được tạo ở đâu?
* lưu ở đâu?
* unique constraint?
* response cũ có được trả lại không?
* key hết hạn khi nào?
* request retry khác payload thì xử lý thế nào?

**Idempotency phải được enforce backend.**

---

# 26. NETWORK FAILURE

Phân tích trường hợp:

```text
Backend commit thành công
↓
Response bị mất
↓
Frontend không biết kết quả
```

Frontend không được blind retry.

Flow an toàn phải là:

```text
Retry/check status
→ tìm transaction theo idempotencyKey
→ nếu đã completed
   trả lại kết quả cũ
→ nếu chưa tồn tại
   xử lý request
```

# 39. STATE MACHINE — ORDER

Thiết kế state machine đầy đủ.

Mặc định có thể:

```text
DRAFT
  │
  │ checkout success
  ↓
COMPLETED
  │
  ├──────────────→ CANCELLED
  │
  └──────────────→ REFUNDED
```

Nhưng phải xác định rõ:

* DRAFT có persistence không?
* Có được edit Order sau COMPLETED không?
* CANCELLED có thể trở lại COMPLETED không?
* REFUNDED có thể CANCELLED không?
* Partial refund có cần state khác không?

Không cho transition không hợp lệ.

Ví dụ:

```text
CANCELLED → COMPLETED
```

mặc định bị cấm.

# 43. STATE TRANSITION AUTHORIZATION

Mỗi transition phải có actor.

Ví dụ:

| Transition                | Actor                  |
| ------------------------- | ---------------------- |
| Order → COMPLETED         | User/Admin             |
| Order → CANCELLED         | Permission-based/Admin |
| Order → REFUNDED          | Admin                  |
| Debt → PAID               | System via DebtPayment |
| Product ACTIVE → INACTIVE | Admin                  |
| Stock adjustment          | Admin                  |
| Session → REVOKED         | Admin / owner tùy rule |

Không cho client tự gửi:

```text
status = PAID
status = COMPLETED
status = REFUNDED
```

và backend chấp nhận trực tiếp.

Backend phải thực hiện transition thông qua business operation.

Cuối tài liệu phải tạo một danh sách tập trung:

```text
INV-001 Stock cannot be negative
INV-002 OrderItem quantity > 0
INV-003 OrderItem subtotal = quantity × unitPrice
INV-004 Order total matches order items/discount
INV-005 Payment amount > 0
INV-006 Payment total cannot exceed Order total unless explicitly allowed
INV-007 Debt original = paid + remaining
INV-008 Debt remaining cannot be negative
INV-009 DebtPayment cannot exceed remaining debt
INV-010 Completed Order cannot be hard deleted
INV-011 Financial history is immutable
INV-012 Stock mutation creates StockMovement
INV-013 Completed checkout atomically affects order/payment/stock/debt
INV-014 Duplicate checkout cannot create duplicate Order
INV-015 Inactive Product cannot be sold
```

Bổ sung các invariant phát hiện được.

# 50. STATE TRANSITION MATRIX

Tạo bảng:

| Entity  | Current State  | Action      | Next State     | Actor            | Transaction | Allowed |
| ------- | -------------- | ----------- | -------------- | ---------------- | ----------- | ------- |
| Order   | DRAFT          | Checkout    | COMPLETED      | User             | Yes         | ✓       |
| Order   | COMPLETED      | Cancel      | CANCELLED      | Admin/permission | Yes         | ✓       |
| Order   | CANCELLED      | Checkout    | COMPLETED      | User             | —           | ✗       |
| Debt    | OPEN           | Partial Pay | PARTIALLY_PAID | User             | Yes         | ✓       |
| Debt    | PARTIALLY_PAID | Full Pay    | PAID           | User             | Yes         | ✓       |
| Debt    | PAID           | Pay         | PAID           | User             | Yes         | ✗       |
| Session | ACTIVE         | Revoke      | REVOKED        | Admin            | Yes         | ✓       |

Không dùng bảng mẫu một cách máy móc; phải phản ánh design thực tế.

# 53. RULE → TEST MAPPING

Mỗi Critical Rule phải có test scenario.

Ví dụ:

```text
INV-001
Given stock = 2
When checkout quantity = 3
Then checkout fails
And stock remains 2
And no completed order exists
```

```text
INV-014
Given idempotencyKey = X
When checkout is submitted twice
Then only one Order exists
And retry returns same result
```

```text
INV-009
Given debt remaining = 50,000
When payment = 60,000
Then payment fails
And debt remains unchanged
```

# 54. MOBILE-SPECIFIC BUSINESS RULES

Không để mobile UX phá business rules.

Ví dụ:

### Double tap

Frontend disable button.

Backend vẫn enforce idempotency.

### Network timeout

Không blind retry.

### Cart stale

Backend revalidate product/price/stock.

### Session expired

Checkout fail an toàn.

### Back navigation

Không được làm mất transaction đã commit.

# 55. PRODUCT IMAGE BUSINESS RULES

Image không phải financial data.

Do đó:

* upload failure không được rollback Product nếu upload được thiết kế hậu kỳ.
* hoặc nếu image là một phần bắt buộc của product creation thì phải nói rõ transaction boundary.

MVP ưu tiên:

```text
Product có thể tồn tại mà không có image.
```

Image là optional.

Không để lỗi thumbnail làm Product không thể bán.

# 56. NOTE BUSINESS RULES

Note:

* optional
* plain text
* không phải financial source of truth
* không thay thế AuditLog
* không thay thế transaction history

Không được dùng Note để encode business state.

Ví dụ cấm:

```text
note = "PAID"
```

thay cho:

```text
Debt.status = PAID
```

# 60. FINAL QUALITY CHECK

Trước khi kết thúc, phải tự kiểm tra:

### Money

Không thể tạo tiền sai hoặc payment vượt rule.

### Debt

Không thể overpay ngoài business rule.

### Stock

Không thể âm do concurrency.

### Order

Không mất snapshot lịch sử.

### Cancellation

Không làm mất financial/stock history.

### Audit

Action quan trọng luôn trace được.

### Security

Không thể bypass permission bằng HTTP request thủ công.

### Idempotency

Retry không tạo duplicate transaction.

### Async

Không có business transaction critical nào bị đẩy sang queue.

### Mobile

Network timeout/double tap không làm sai dữ liệu.

Nếu phát hiện inconsistency giữa Use Case và Entity:

**phải nêu ra thay vì tự âm thầm sửa.**

---

# FINAL PRINCIPLE

Thiết kế Business Rules sao cho:

> **Mọi transaction tài chính và tồn kho đều deterministic, atomic, traceable và retry-safe.**

Và thiết kế State Machine sao cho:

> **Không có state transition "lách luật" chỉ vì frontend gửi một status khác.**

Mục tiêu không phải tạo nhiều rule.

Mục tiêu là tạo **ít rule nhưng đúng, rõ và đủ mạnh để bảo vệ POS trong thực tế.**
