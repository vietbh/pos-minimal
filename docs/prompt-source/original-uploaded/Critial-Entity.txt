# 5. FORMAT CHO TỪNG ENTITY

## Entity: Product

### Purpose

### Responsibility

Entity chịu trách nhiệm nghiệp vụ nào?

### Attributes

| Field | Type | Required | Nullable | Default | Unique | Index | Description |
| ----- | ---- | -------- | -------- | ------- | ------ | ----- | ----------- |

### Relationships

Mô tả:

```text
Product 1 ── N OrderItem
Product 1 ── N StockMovement
```

### Lifecycle

Entity có state/status không?

### Business Invariants

Ví dụ:

```text
stockQuantity >= 0
sellingPrice >= 0
SKU unique
```

### Mutable Fields

Field nào có thể sửa?

### Immutable Fields

Field nào không được sửa sau khi tạo?

### Audit Requirements

Thay đổi nào phải audit?

### Used By

Use Case nào sử dụng Entity này?

# 11. DEBT

Debt phải đại diện cho **một khoản nợ phát sinh từ một Order**.

Mô hình:

```text
Customer
   │
   ├── Debt → Order
   ├── Debt → Order
   └── Debt → Order
```

Không sử dụng:

```text
Customer.totalDebt
```

làm source of truth.

Thiết kế:

```text
id
customer
order
originalAmount
paidAmount
remainingAmount
dueDate
status
createdAt
updatedAt
```

Phải quyết định:

### Status

Đề xuất:

```text
OPEN
PARTIALLY_PAID
PAID
```

`OVERDUE` nên cân nhắc là derived state:

```text
remainingAmount > 0
AND dueDate < now()
```

Không tạo trạng thái OVERDUE nếu không cần lưu persistence.

Giải thích quyết định.

---

# 12.1 DEBT BALANCE

Phải xác định:

```text
originalAmount
paidAmount
remainingAmount
```

có cần lưu cả 3 không.

Nếu lưu:

```text
remainingAmount = originalAmount - paidAmount
```

phải đảm bảo invariant.

Không cho:

```text
paidAmount > originalAmount
remainingAmount < 0
```

trừ khi business rule explicitly cho phép overpayment.

# 22. OWNERSHIP

Phải xác định Entity ownership.

Ví dụ:

```text
Order
 └── OrderItem
```

OrderItem không có ý nghĩa nếu không có Order.

Do đó cân nhắc:

```text
Order 1 → N OrderItem
```

với lifecycle phụ thuộc Order.

Tương tự phân tích:

* DebtPayment → Debt
* StockMovement → Product
* Payment → Order

* cascade persist?
* cascade remove?
* orphan removal?
* restrict?
* set null?

Đặc biệt:

**Không cascade delete financial history một cách nguy hiểm.**

Ví dụ:

Không cho:


# 35. NO SOFT DELETE BY DEFAULT

Không tự động thêm:

```text
deletedAt
```

vào mọi Entity.

Chỉ dùng soft delete khi có lý do nghiệp vụ.

Product có thể dùng:

```text
isActive
```

thay vì delete.

Order, Payment, Debt, StockMovement, AuditLog không được hard delete trong flow bình thường.

# 37. PERFORMANCE

Entity design phải phù hợp mobile-first nhưng không optimize quá sớm.

Ưu tiên:

* index đúng
* tránh N+1
* lazy/eager loading có chủ đích
* pagination
* query DTO/read model khi cần
* không load toàn bộ relationship chỉ để hiển thị list

Không biến Entity thành object graph khổng lồ.

Có thể thanh toán vượt nợ không?

### Audit

Có thể thay đổi lịch sử mà không trace được không?

### Delete

Có thể xóa mất financial history không?

### Mobile

Entity có khiến một thao tác đơn giản phải tạo quá nhiều request không?

### Async

Có entity nào đang bị tạo chỉ vì Messenger mà không có lý do domain không?

Nếu phát hiện vấn đề, sửa design trước khi kết luận.

**Mục tiêu cuối cùng: một Domain Model nhỏ, rõ, transaction-safe và đủ linh hoạt cho Mobile POS — không phải một database khổng lồ.**
# BỔ SUNG CRITICAL PROMPT — IMAGE UPLOAD & NOTE/COMMENT

Bổ sung vào **Entity & Domain Model Specification** của Mobile POS.

Mục tiêu vẫn giữ nguyên:

**Mobile-first → ít thao tác → ít request → đơn giản → data integrity.**

Không biến chức năng upload hình hoặc note thành hệ thống CMS/comment phức tạp.

---

# 1. PRODUCT IMAGE

Product cần hỗ trợ upload hình ảnh.

Mục đích chính:

* Nhận diện sản phẩm nhanh trên POS.
* Hiển thị hình trong product card.
* Hiển thị hình trong product detail.
* Hỗ trợ người bán chọn sản phẩm nhanh hơn trên điện thoại.

## Product Image Requirements

Không nên lưu binary image trực tiếp trong MySQL.

Database chỉ lưu metadata/reference.

File thực tế lưu trên filesystem/object storage tùy infrastructure.

Entity có thể thiết kế:

```text
Product
   │
   └── ProductImage
```

Hoặc nếu MVP chỉ cần một ảnh:

```text
Product
 └── image
```

Hãy phân tích cả hai phương án và chọn phương án phù hợp với MVP.

Ưu tiên phương án đơn giản nhưng không khóa khả năng mở rộng.

# 3. IMAGE SECURITY

Upload phải được validate ở backend.

Không tin:

* filename từ client
* MIME type từ client
* extension từ client

Phải kiểm tra:

* file có thực sự là image hay không
* MIME type
* extension
* file size
* image dimensions nếu cần

Không cho upload file executable/script giả dạng image.

Tên file lưu storage nên được generate bởi server.

Không dùng original filename làm tên file vật lý nếu có rủi ro collision/security.

---

# 4. IMAGE UPLOAD UX

Mobile-first.

Không tạo form upload phức tạp.

Product form:

```text
[ Ảnh sản phẩm ]

[ Chụp ảnh ] [ Chọn từ máy ]

Tên sản phẩm
Giá bán
Tồn kho

[ LƯU ]
```

Nếu browser/device hỗ trợ camera, có thể cho phép:

```text
capture
```

nhưng không bắt buộc.

Có preview trước khi upload.

Nếu upload ảnh cùng lúc tạo product:

```text
User chọn/chụp ảnh
        ↓
Preview
        ↓
Submit product
        ↓
Backend lưu Product
        ↓
Lưu image
```

Không tạo nhiều HTTP request không cần thiết.

Nếu cần xử lý resize/compression thì có thể cân nhắc async.

---

# 5. IMAGE PROCESSING

MVP:

* Không cần image processing phức tạp.
* Có thể resize ảnh lớn để tiết kiệm storage/bandwidth.
* Không cần tạo hệ thống CDN riêng.

Nếu xử lý ảnh mất thời gian:

```text
Upload
 ↓
Save original/reference
 ↓
Dispatch ProcessProductImageMessage
 ↓
Worker resize/compress
```

Nhưng:

**Không queue việc cần thiết để xác nhận product đã được tạo thành công.**

Nếu product creation và image upload có thể commit an toàn trong cùng request thì ưu tiên cách đơn giản.

# 10. NOTE CHO ORDER

# 15. NOTE VS AUDIT LOG

Phải phân biệt rõ.

### Note

Do user chủ động nhập.

Ví dụ:

```text
Order.note
"Khách yêu cầu giao buổi tối"
```

### AuditLog

Do hệ thống ghi nhận.

Ví dụ:

```text
User A
changed Product price
from 10,000
to 12,000
```

Không dùng Note để thay thế AuditLog.

Không dùng AuditLog để thay thế Note.

---

# 16. NOTE VS BUSINESS DATA

Không lưu business data quan trọng chỉ trong note.

Không làm:

```text
Debt.note = "Khách nợ 500k"
```

mà không có:

```text
Debt.remainingAmount = 500000
```

Không làm:

```text
Order.note = "đã trả 100k"
```

thay cho:

```text
Payment.amount = 100000
```

Note chỉ là contextual information.

Business data phải nằm ở field/entity tương ứng.
