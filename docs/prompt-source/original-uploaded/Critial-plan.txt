# CRITICAL PROMPT — XÂY DỰNG MOBILE-FIRST POS

Bạn là Senior Symfony Architect + Backend Engineer + Mobile UX Engineer.

Hãy xây dựng một **Web POS nhỏ, mobile-first** bằng **Symfony 7.4 + MySQL + Doctrine ORM + Twig + Stimulus + Symfony Messenger**.

## 0. TƯ TƯỞNG CỐT LÕI

Đây **không phải ERP thu nhỏ**.

Đây là một POS nhỏ với mục tiêu:

> **Bán hàng nhanh nhất có thể, ít thao tác nhất có thể, ít request nhất có thể, dữ liệu tiền/kho/công nợ tuyệt đối nhất quán.**

# 7. CHECKOUT TRANSACTION

Checkout phải là database transaction atomic.

Flow:

```text
POST /pos/checkout
 ↓
Validate request
 ↓
Load products
 ↓
Lock/check stock
 ↓
Resolve authoritative prices
 ↓
Calculate totals
 ↓
Create Order
 ↓
Create OrderItems
 ↓
Deduct Stock
 ↓
Create StockMovements
 ↓
Create Payment
 ↓
Create Debt nếu còn nợ
 ↓
Create AuditLog
 ↓
COMMIT
```

Nếu một bước lỗi:

```text
ROLLBACK EVERYTHING
```

Không được xảy ra:

* Order tồn tại nhưng stock chưa trừ.
* Stock đã trừ nhưng order fail.
* Payment tồn tại nhưng debt sai.
* Debt tồn tại nhưng transaction không có order.

# 8. STOCK CONCURRENCY

Phải chống race condition.

Không chỉ:

```php
if ($stock >= $quantity)
```

rồi update.

Sử dụng transaction + locking hoặc atomic SQL phù hợp.

Ví dụ:

```sql
UPDATE product
SET stock = stock - :quantity
WHERE id = :id
AND stock >= :quantity
```

Sau đó kiểm tra affected rows.

Hai người cùng bán sản phẩm cuối cùng không được làm stock âm hoặc bán vượt tồn.

# 38. FINAL PRINCIPLE

Luôn hỏi:

> "Có thể giảm một thao tác không?"

> "Có thể giảm một request không?"

> "Có thể xử lý việc này async không?"

> "Có làm ảnh hưởng tính nhất quán tiền/kho/công nợ không?"

Nếu có thể giảm thao tác/request mà không ảnh hưởng correctness → giảm.

Nếu async được mà không ảnh hưởng kết quả người dùng cần ngay → đưa vào Messenger.

Nếu liên quan đến tiền, order, debt hoặc stock → ưu tiên atomic synchronous transaction.

**Build a fast mobile POS, not a miniature ERP.**
